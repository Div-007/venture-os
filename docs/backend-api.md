# Backend API and contract seams

All product routes use `/v1`, return `{ ok: true, data }`, and use the shared safe error envelope on failure. Malformed JSON returns 400 and an oversized body returns 413 (both `BAD_REQUEST`); a unique-index violation that a route does not translate itself returns 409 `CONFLICT` and is logged as a `duplicate_key` warning. Dates are ISO 8601 strings at the HTTP boundary and IDs are stable opaque strings.

Cursor-paginated lists return `{ ok: true, data: { items, nextCursor? } }`; other purpose-built read models use their exported shared schemas. The contracts package exports `sessionBootstrapResponseSchema`, `dashboardResponseSchema`, and the generic `pagedSuccessEnvelope` helper.

## Identity and hierarchy

- Better Auth is mounted at `/api/auth/*`; magic-link email uses Resend when configured and a labelled local logger otherwise.
- `POST /v1/invitations/accept` attaches an authenticated Better Auth user to the app-owned membership from an admin invitation.
- `GET /v1/members` returns a paged, active-member directory with `id`, `name`, optional `handle`, and `role` (no email). Workspace-wide lookup supports DMs; `ventureId` and `groupId` filters require access to that scope. `handle` is a case-insensitive exact lookup; `q` searches names and handles. Exact lookup rejects duplicate handles in scope with 409 rather than choosing a member arbitrarily.
- Run `npm run migrate --workspace @venture-studio/api` after upgrading an existing database, with out-of-band handle writers stopped for the run. Migration `002-user-handles` fills missing handles in deterministic workspace/user-ID order: a sanitized name slug where free, otherwise a stable ID-hash suffix extended on collision. Existing nonempty handles remain unchanged; each change has a `user.handle.backfill` audit event. The sanitized development seed runs the same backfill using its short demo aliases when free and no longer overwrites existing handles on reseed. If legacy data already has duplicate handles, resolve them manually; command execution rejects an ambiguous in-group match with 409. Migration `003-string-dates` converts ISO strings that earlier create routes stored in `tasks.dueAt/reviewAt`, `outcomes.startAt/reviewAt`, `decisions.decidedAt`, `classes.scheduledAt`, and `information_requests.dueAt` into BSON dates (compare-and-set; unparseable values are left for manual review). Create routes now store these fields as dates, matching updates and seeds. The migration is idempotent; rerun it after a rolling deploy in case an older instance wrote strings meanwhile.
- `GET /v1/session/bootstrap`, `GET /v1/hierarchy`, `GET /v1/dashboard` return the current user, role, authorized hierarchy, and canonical Today read model.
- Admin routes create invitations and ventures. `POST /v1/admin/groups` creates a group with `#general`; `POST /v1/admin/channels` accepts `{ groupId, name }` and creates an additional slugged channel (409 on a duplicate within the group).
- `GET /v1/admin/memberships` lists workspace memberships. `PUT /v1/admin/memberships/:id` replaces `{ role, ventureIds, groupIds }` for another active member. Groups must belong to assigned ventures; admins cannot edit their own membership through this route. The shared inputs are `createChannelSchema` and `updateMembershipSchema`.

## Collaboration and work

- Channel messages: `GET|POST /v1/channels/:channelId/messages`; direct messages: `GET /v1/direct-messages/:userId` (latest 100, chronological response), `POST /v1/direct-messages`.
- Channel history accepts `?pinned=true` or `?threadRootId=<id>` in addition to the ordinary cursor/limit query. By default it pages forward from the oldest message; `?order=latest` returns the newest page in chronological order and its `nextCursor` loads the next older page (the connected chat uses this mode). `PUT /v1/messages/:id/reaction` accepts `{ emoji, active }`; `PUT /v1/messages/:id/save` accepts `{ saved }`; `PUT /v1/messages/:id/pin` accepts `{ pinned }`. `GET /v1/messages/saved` returns up to 100 saved, still-visible messages for the caller. Message reads include `reactions` (emoji-to-count map), `myReactions`, `savedByMe`, `pinned`, and optional `pinnedAt`/`pinnedBy`. Pins require an admin or venture head in a channel; reactions require message-write permission and saves require current message access. DM pins are unsupported.
- Socket.IO authorizes the initial connection and every `channel:join`; it emits channel-scoped presence, and `message:create` persists the message/event/outbox before emitting. Every channel/user fan-out rechecks the current session and membership. Browser clients authenticate through the Better Auth cookie. Local development also accepts `auth: { devUserId }` when `ALLOW_DEV_AUTH=true`; production ignores it. Socket requests carrying an Origin must match `APP_ORIGIN`. The web deployment must proxy `/socket.io` (including WebSocket upgrade) on the same origin as its auth cookie; the current Next rewrite only covers HTTP routes. Message history uses a total `(createdAt, id)` cursor order and `clientId` retries return the canonical prior result.
- Channel messages notify only validated `@mentions`; ordinary channel activity appears in the channel itself, and DMs always notify the recipient. Workspace admins are in scope for every channel, so they can be mentioned. The `messages` notification preference therefore covers direct messages only.
- Thread replies require an existing top-level root in the same channel or DM conversation. DM `clientId` retries also return the canonical message. REST and socket message creation, reactions, and pins emit authorized Socket.IO `event` payloads after persistence, and are also replayable through `GET /v1/events`; personal saves are not broadcast. Connected clients should resume from the event cursor after reconnect. `GET /v1/events` without `after` returns the newest 500 visible events (ascending) so a client can establish its cursor at the present rather than deep in history.
- Tasks: `GET|POST /v1/tasks`, `GET|PATCH /v1/tasks/:id`, comments, evidence submission/review, saved task filters, and outcome routes. Evidence submission validates `createEvidenceSchema`: an optional `uri` must use `http` or `https`, and an absent URI is omitted rather than stored as null. Legacy `uri: null` evidence and `nextActionAt: null` opportunities are omitted from responses, and new opportunities without a next-action date omit the field.
- Focus: `POST /v1/focus`, `GET /v1/focus/current`, `GET /v1/focus/history` (paged completed sessions, caller only), `POST /v1/focus/:id/complete`.
- Commands: `POST /v1/commands/preview`, then `POST /v1/commands/execute` with an idempotency key.
- `/assign @handle` and `/notify @handle` resolve active members of the command channel's venture and group at execution time. Handle matching is case-insensitive; email and exact name remain fallbacks only when no handle matches. Ambiguous matches fail with 409, and out-of-scope recipients fail with 404. Typed channel `@mentions` resolve through the group-scoped member directory before sending `mentionUserIds`.
- Command preview accepts `/notify @ashutosh 1h "task details"` (or `10m`) and `/assign @ashutosh "task details" 90m 2026-09-25T10:00:00Z` (or `1h`). Delays/estimates must be positive whole minutes or hours, at most 100,800 minutes; assignment deadlines must be future ISO 8601 timestamps with an offset. Existing `/notify @user "message" at=<ISO>` and `/assign @user "task" due=<ISO> estimate=<minutes>` remain valid. `timezone=<IANA>` remains optional for both. Preview returns 400 with a useful syntax/timing message for invalid or mixed forms; execute returns `STALE_PREVIEW` if the scheduled time passed after preview. Relative delays become absolute at preview and are not recalculated on execute or retry. Reusing an idempotency key with the same preview replays its result; using it for a different preview returns 409.
- Reminders: `GET /v1/reminders` (paged, caller only), `GET /v1/reminders/:id` (caller only), and `POST /v1/reminders/:id/snooze` accepting `10`, `20`, `30`, or `never`. Task-reminder notifications preserve `resourceType: "task"` and `resourceId: taskId`, and now also carry `reminderId` for snooze actions.

## Knowledge, operating records, and search

- Versioned Markdown: `POST /v1/documents`, `GET /v1/documents` (authorized paged metadata, optional `ventureId`/`status`), `GET|PUT /v1/documents/:id`, and metadata approval at `PATCH /v1/documents/:id/metadata`.
- `PUT /v1/documents/:id` accepts an optional `baseVersionId` (the version the editor opened). If another version was saved since, the update fails with 409 `CONFLICT` and nothing is overwritten; the connected editor always sends it. Clients that omit it keep last-writer-wins behaviour, but version numbers are assigned inside the transaction so concurrent saves never share one. Blank (whitespace-only) Markdown is rejected with 400.
- Version `sourceUri` is omitted when absent; legacy stored `null` values are omitted from document detail responses. Supplied URLs are preserved.
- Document scope: missing or legacy `null` `ventureId` means workspace-wide; API responses omit the field for either form. Admins see every venture in their workspace without a venture filter; an explicit venture filter includes that venture plus workspace-wide documents. Non-admins see workspace-wide documents plus only their assigned ventures, subject to sensitivity. Only admins may create, edit, or approve workspace-wide documents.
- Authorized cited retrieval: `GET /v1/knowledge/search`; bounded export: `GET /v1/context-packets/tasks/:id`.
- Cross-resource authorized search: `GET /v1/search` for tasks, messages, and ready file metadata.
- Decisions, classes/applied assignments, information requests, outcomes/timeline records, pipelines, and opportunities use their named `/v1` route groups. `PATCH /v1/decisions/:id`, `/classes/:id`, `/outcomes/:id`, `/pipelines/:id`, and `/opportunities/:id` accept non-empty partial updates from the exported `update*Schema` contracts. Venture scope is immutable; decisions/classes/outcomes/pipelines require an admin or venture head in scope, while an opportunity owner may also update their own record. All updates return the updated record.
- Class creation and updates require every facilitator/participant to be an active member of the class venture. Class lists, Today, dashboard, applications, and MCP schedules also enforce current venture access; workspace-wide classes remain available to their participants.
- `GET /v1/classes/:id` provides authorized detail. `POST /v1/classes/:id/applications` requires a different active same-venture reviewer. `GET /v1/classes/:id/applications` is paged; applicants see their own submissions, assigned reviewers theirs, and the facilitator/admin/venture head all in scope. `GET /v1/classes/:id/applications/:applicationId` and `PATCH /v1/classes/:id/applications/:applicationId/review` provide detail and an audited assessment (`{ assessment, nextGap? }`). Assigned reviewers can discover these classes through `GET /v1/classes`.

## Files, notifications, and MCP

- `GET /v1/files` returns cursor-paginated, ready file metadata for the caller's authorized ventures and groups. `ventureId` narrows the library; direct-message attachments are excluded. The response uses the public file contract and never exposes storage keys. Knowledge displays these files beside Markdown records, but uploading a binary file does not create an approved evidence record.
- `POST /v1/uploads` creates constrained metadata and a short-lived upload URL, optionally linked to a same-scope task; recoverable completion rechecks metadata and promotes staging through `pending -> finalizing -> ready`; `GET /v1/files/:id/download` authorizes metadata before signing.
- Local object URLs are HMAC-signed and operation-scoped. Production uses Cloudflare R2 credentials and refuses the local adapter.
- Browser uploads to R2 also require a bucket CORS policy for the web page's exact origin, independent of a valid presigned URL. Allow `PUT`, `GET`, and `HEAD`, allow the `Content-Type` request header, and expose `ETag` so the client can complete the upload. The `venture-studio-dev` bucket allows both local preview origins `http://localhost:3011` and `http://localhost:3012`; add the deployment origin to the appropriate bucket before using a different host or port. Keep production bucket policy separate.
- `GET|PUT /v1/notification-preferences` exposes separate message, mention, assignment, reminder, email, and Web Push controls. Push is at-least-once and includes stable `notificationId` for client deduplication.
- Local development PATs are created/revoked under `/v1/pats`. The stdio MCP exposes ten read-only tools with PAT scope, membership filtering, citations, revocation, and audits. Hosted access must replace PATs with OAuth.
