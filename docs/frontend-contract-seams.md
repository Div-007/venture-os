# Frontend contract seams

The Phase 2 demo UI runs on browser-local records under `apps/web/src/lib/studio-demo.ts` and `studio-store.tsx`. It remains a reviewable interaction prototype, not an authorization layer or API cache. The separate `/live` routes use server-owned records and published contracts; demo activity, reminders, and preferences do not prove backend behavior.

## Read models needed

| UI consumer | Backend capability needed | Key semantics |
| --- | --- | --- |
| Shell, Dashboard, Today, Ventures | Session bootstrap and workspace hierarchy | Stable opaque IDs; effective roles; venture → group → inherited channels; venture freshness and selected context |
| Dashboard, Today, Tasks, Board, Timeline | Authorized task and outcome lists/detail | One canonical task in all views; cursor filters for venture, group, person, tag, status, due range; absolute dates and server timestamps |
| Channels and DMs | Channel/DM history and realtime subscriptions | Server join authorization, thread parent, mentions, reactions, pins/saves, reconnect cursor |
| Notifications | Personal inbox and preference read | Read/snooze/delivery states, absolute scheduled time, IANA timezone, source record ID |
| Knowledge | Authorized Markdown search and detail | Source ID, evidence class, sensitivity, owner, version history, last review, related records; exclude inaccessible results on the server |
| Decisions, Classes, Requests, Sales | Venture-scoped lists/detail | Canonical IDs and source links; class assessment is distinct from attendance; pipeline is partitioned by venture |
| Admin, sign-in, invite | Identity and membership reads | No trust in client-selected demo identity; group subset of venture membership; role scope and server audit records |

## Mutations needed

- Task create/update/accept, evidence attachment, blocker, status, reminder, snooze, and completion. Completion must reject missing evidence unless a recorded exception is permitted.
- Group/venture/channel creation and membership/role changes with server checks and audit identity.
- Message/thread send, mention resolution, reactions, pins, and saves. `/assign` and `/notify` require typed server preview followed by execution with an idempotency key; the client command preview is only a demo. The connected composer can show `/notify @person 1h "message"` and `/assign @person "task" 90m <ISO deadline>` alongside the older `at=`, `due=`, and `estimate=` forms; display the server's 400 timing/syntax message and `STALE_PREVIEW` response without guessing a schedule locally.
- Knowledge create/edit/import/export. Version increments and sensitivity enforcement must be server-owned.
- Decision, class, outcome, request, and pipeline edits return the canonical updated record.
- Invite issuance/acceptance, notification preferences, scoped PAT creation/revocation, and focus-session recovery require backend services; corresponding UI surfaces are explicitly labelled unavailable or demo-only until connected.

The connected integration uses the shared Zod envelope and error format from `packages/contracts`. Do not derive API field names from the temporary demo types without a contract review.

The web app reserves same-origin `/v1/*`, `/api/auth/*`, and `/socket.io` rewrites for the API, using server-side `VSO_API_ORIGIN` (default `http://localhost:4000`). The Socket.IO client deliberately uses HTTP polling, not a WebSocket upgrade; this works through the Next rewrite without a separate browser-facing API origin. A deployment with multiple API instances must provide sticky polling-session routing (or start with one API instance). Deployment behind a production reverse proxy and browser cookie authentication still need staging verification.

Connected pages live under their own `(connected)` layout, with workspace hierarchy and identity from authenticated bootstrap rather than the demo store. `/dashboard/live` reads the dashboard and paged tasks. `/tasks/live` and `/board/live` share canonical task IDs, filters, status updates, comments, evidence submission/review, and scoped member assignment/reviewer discovery. `/channels/live` reads/sends authorized messages, resolves exact `@handle` mentions through the member directory, replies in threads, reacts, saves, and pins when permitted, and requires a typed `/assign` or `/notify` preview before execution. `/messages/live` selects active workspace recipients, reads the latest 100 DM messages, and supports idempotent sends and thread replies. Both collaboration views refresh from authorized realtime events, replaying the server cursor on reconnect; a manual Refresh remains available. The browser received a second local member's channel post over same-origin polling without reload. Older DM paging, a dedicated pinned/saved collection, and browser-cookie Socket.IO verification remain open.

`/notifications/live` reads and marks notifications, lists reminders, reads/updates delivery preferences, and snoozes task reminders using their explicit reminder IDs. `/focus/live` starts, recovers, and completes server sessions and lists paged completed history. `/knowledge/live` browses paged authorized document metadata, searches approved/stale evidence, reads the current document version plus version metadata, and edits a document into a new draft. Admins and scoped venture heads can use audited approval/stale metadata controls. Historical version text and a general file list are not available through the API; the UI labels those limits and offers authorized file-name search instead. Venture-scoped files use the signed upload-intent, object PUT, completion, authorized signed-download sequence. `/tasks/live` additionally shows task-scoped attachments and supports the same upload/download sequence. An attachment does not silently become accepted evidence: after upload the evidence form is prepared with its file ID, and a reviewer must separately assess the submitted note. `/planning/live` reads outcomes, decisions, classes, and information requests, updates statuses when permitted, shows a date-based timeline, and supports class application/assessment review. `/sales/live` reads and updates venture-scoped pipelines and opportunities. `/admin/live` manages memberships and channels with server validation. `/sign-in/live` requests a Better Auth magic link; `/invite/live` accepts a token only with a real session, not the local development header. All validated response paths use published contracts where schemas exist, and failures never fall back to demo records.

Local browser QA uploaded a synthetic 102-byte text file, found it through authorized file search, and prepared its signed download. An independent authorized GET returned the same SHA-256 as the source. The in-app browser did not emit a save/download event or a visible Downloads file after the final link click, so the physical browser-save step remains unverified. The synthetic local file record remains in the development database; the source fixture was removed from the worktree. A scoped venture head opened and approved a synthetic Buildory document through the live drawer; its status changed to approved and the dialog returned keyboard focus on Escape. The response adapter normalizes `sourceUri: null` to absent for published optional-version validation. The backend task has the contract mismatch and a separate admin filter defect: `authorizedDocumentFilter` excludes venture documents for unfiltered admins and excludes workspace documents stored with `ventureId: null`. Two synthetic QA documents remain in the local database to reproduce this. No frontend workaround guesses admin document access.

The local browser preview sends the backend's opt-in `x-dev-user-id: user-divyansh` header on `localhost` for product REST routes; the backend prefers a real session cookie when present. For Socket.IO, the browser first checks for a real Better Auth session and sends a local-development identity only if no cookie session exists. Production uses the cookie only. The development header is deliberately disabled for invitation acceptance. The demo pages remain browser-local and labelled. Sanitized seed data has no documents, applications, reminders, or DM history, so their empty/read views were inspected in the browser while their mutation contracts are covered by the Mongo-backed API suite rather than a populated browser walkthrough. Full operating-record editing remains a later integration seam.
